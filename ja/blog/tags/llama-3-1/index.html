[マウムジギ 開発日誌 #9] Llama 3.1ファインチューニングのエラーとの死闘と6週目中間発表

2026年4月9日 · 約3分
jbgih
Antigravity Developer

4月9日、昨日野心的に完成させたColabノートブックを使って、ついに人工知能モデル（Llama 3.1）の最初の学習（ファインチューニング）を試みました。しかし、現実はやはり甘くなく、数多くのエラーに直面しなければなりませんでした。同時に卒業研究6週目の中間発表資料まで作らなければならない過酷な一日でした。

Colabファインチューニングエラーとの終わりのない死闘​

  • 問題: 昨日作成したllama31_finetuning_colab.ipynbを実行するやいなや、各種エラーが降り注ぎました。
  • 過程:

    「llama31_finetuning_colab (3).ipynbでM1ファインチューニングの進行中にエラーが発生した理由は何でしょうか？」 「実行した結果にeos_tokenが含まれています。なぜこのような問題が発生するのでしょうか？」

  • 結果: AIモデルが学習データを吐き出す過程で特殊トークン（eos_token）の処理が正しく行われない問題、メモリオーバーフロー問題などが立て続けに発生しました。発生したエラーログ全体をClaudeにコピーして投げ（Pasted text）、解決策を受け取ってコードを修正するプロセスを何度も繰り返しました。結局、紆余曲折の末に学習が完了し、学習データ別学習結果.pngという意味のある結果グラフを抽出することができました！

AIアシスタントの発表資料(PPT)作成​

  • 問題: モデル訓練で徹夜している中、すぐに来週の発表のために6週目のフロントエンドとデータベースの進行状況PPTを作成しなければなりませんでした。
  • 過程:

    「キャプディ_6週目_Frontend.pptxはこれまで進行した概要を紹介する画像集です。これを活用して今週の進行状況の発表資料を作ってください。」 「データベース設計のテーブルをbackendに実装されたテーブルの関係を参考にして関係が見えるように表現して... テーブルが大きすぎてバラバラです。Userテーブルを中心にして配置してください。」

  • 結果: 驚くべきことに、AIはフロントエンドの画像スクリーンショットを組み合わせて発表スクリプトとスライドの骨組みを作ってくれました。さらに、私がバックエンドコードに基づいて複雑なデータベースERD（Entity Relationship Diagram）を描いてほしいと執拗にフィードバック（User中心配置）を与えると、完璧にデータベース関係図まで整理して説明してくれました。

今日はLlama 3.1という最新の言語モデルを直接自分の手（とAIの頭）でチューニングしてみる快感を感じた日です。同時に、コーディングだけでなく発表資料の作成、DBアーキテクチャ図の設計まで、AIを100％活用する方法を身につけています。果たして私たちのマウムジギAIはどれくらい賢くなったのでしょうか？次回、そのテスト結果を公開します！

[マウムジギ 開発日誌 #8] API料金爆弾事件とColabファインチューニング準備

2026年4月8日 · 約3分
jbgih
Antigravity Developer

4月8日は、マウムジギプロジェクトを進める中で最大の危機であり、「笑えない」ハプニングが発生した日です。それはまさにClaude API月間限度額超過および料金爆弾事件です。

バックグラウンドの裏切り：「10件生成に1ドルだと？」​

  • 問題: 昨日最適化を終えたと安心し、大規模なテストデータセット生成スクリプトをバックグラウンドでオンにしたまま放置しました。
  • 過程:

    「問題：月間限度額を超過して費用が請求されている。バックグラウンドでAPIが動いていると思って放っておいたらこんなことになった。」 「いや、10件生成するのに1ドル消費されるなんてあり得るか？」

  • 結果: LLMを使って高品質のカウンセリングデータを合成（Synthesis）する過程で、プロンプトのコンテキスト（入力トークン）が蓄積され、コストが幾何級数的に増加したのです。月間決済限度額を超過してスクリプトが停止する事態が発生し、結局AIに「リアルタイムで予想消費量と費用、進行状況をコンソールに出力し、限度額超過を防止する機能を今すぐ追加しろ」と緊急指示を下しました。クラウドやAPIを使用する際、料金モニタリングがどれほど重要か骨身に染みて感じました。

Llama 3.1訓練のためのColabノートブック作成​

  • 問題: データが準備されつつあるので、今度は実際にLlama 3.1モデルをファインチューニング（Fine-Tuning）するコードが必要でした。ローカルPCのGPUでは到底足りないため、Google Colab環境を使用しなければなりませんでした。
  • 過程:

    「llama31_finetuning_experiment_plan_revised.mdをColabで進行するためのpython notebookを作成してください。」 「訓練dataをtrain/val/testではなくtrain/valにのみ分割し、9:1の比率で分ける。」

  • 結果: AIが自ら訓練計画書を読み、llama31_finetuning_colab.ipynbという完璧なJupyter Notebookコードを書いてくれました。Unslothなどの最新軽量化ライブラリをセットアップし、データセットを9:1の比率で分割して学習と検証に使用するロジックまで完璧に実装しました。

今日はAPI料金爆弾という恐ろしい通過儀礼を経て、プロジェクトの現実的な壁を乗り越えた一日でした。しかし、その代償として素晴らしいデータセットとファインチューニング用のColabノートブックが完成しました。ついに次の段階は、本物の人工知能モデルを訓練（Training）することです！

[マウムジギ 開発日誌 #5] 10万件の感情データ精製とAPIコストの重圧

2026年4月3日 · 約3分
jbgih
Antigravity Developer

4月3日、ディープラーニングモデル（Llama 3.1）に学習させるための対話データを精製する作業に本格的に着手した日の記録です。 単にデータを統合するだけでなく、AIにテキストを読ませて自ら感情を判別させる巨大なパイプラインを稼働させた日でもあります。

データ感情の再分類 (v3 -> v4)​

  • 問題: 既存のデータセットの感情ラベリングが、私たちの目指すきめ細かい心理カウンセリングの目的に正確に合致していませんでした。合計100万件のデータの中から意味のあるデータのみをフィルタリングし、正確な感情をマッピングする必要がありました。
  • 過程:

    「範囲は全体の100万件です... Claudeが心理カウンセリングの専門家として会話を読み、直接感情をマッピングするためです。感情分類に含まれないものは除外し、含まれるものだけをフィルタリングします。」

  • 結果: v4_plan.mdを作成し、作業を開始しました。一次的に10万行のデータを対象にClaude APIを連動させ、対話の文脈を把握し感情を再分類するスクリプトを作成・稼働させました。

LLM API課金の恐怖​

  • 問題: 膨大なテキストデータをLLM（Claude）に投げて判別させるため、API使用量（トークン数）が幾何級数的に増加する問題が発生しました。
  • 過程:

    「すでにPro購読でClaudeを使用中ですが、APIが別途必要ですか？」 「Anthropic APIではなくClaude Codeを使用する方法はありませんか？ 課金が負担です。」 「実際の費用は10.27ドルでした。」

  • 結果: Claude Pro購読（月額20ドル）とは別に、Pythonスクリプトで自動化して大量のデータを処理するために呼び出すAnthropic APIは、使用量に応じた従量課金制であるという痛烈な事実を体感しました。わずか10万行をテスト処理するだけで、瞬く間に約10.27ドルが課金されました。100万件すべてを処理するには莫大な費用がかかることを悟り、モデルの最適化とデータサンプリングの重要性を肌で学んだ一日でした。

今日は、ディープラーニングのデータ前処理過程で必然的に直面する「コンピューティングコスト」という現実的な壁にぶつかった日でした。 結果的に精製された良質なデータを得ることには成功しましたが、今後どのようにこのコストと効率性のバランスを取りながらファインチューニングを進めていくか、深い悩みを抱かせる貴重な経験となりました！

[マウムジギ 開発日誌 #4] ファインチューニングデータ前処理の本格稼働

2026年4月1日 · 約3分
jbgih
Antigravity Developer

マウムジギプロジェクトの中核エンジンとなるLlama 3.1モデルを訓練するため、膨大な量の対話データをモデルが学習できる形式に加工し始めた4月1日の記録です。

データ前処理計画に基づく自動化の実行​

  • 問題: モデルをファインチューニングするためには、ユーザーの発話とチャットボットの応答が含まれた生データを、Llama 3.1が理解できる特殊なJSONL形式に完璧に変換する必要がありました。
  • 過程:

    Claude Codeへ: 「llama31_finetuning_data_preprocessing_plan_short.mdに従って作業を進行」

  • 結果: 昨日作成した前処理計画書に基づき、AIエージェントが自らデータクレンジングおよび加工パイプラインを構築し、実行し始めました。人が数万件のデータをいちいち手作業で変換する代わりに、ルールが記されたMarkdown文書を1つ渡し、「この通りに処理して」と指示する方式です。

カテゴリデータの統合とJSONL変換​

  • 問題: 前処理過程は複数の段階（Step）に分かれており、最終的にすべてのデータを1つに統合して訓練用データセットを完成させる必要がありました。
  • 過程:

    Claude Codeへ: 「Step 4を実行して。2つのカテゴリデータを統合してLlama 3.1 JSONL形式に変換して。」

  • 結果: AIが即座にStep 4を実行し、散らばっていた各カテゴリの対話データを1つにマージしました。そして、Llama 3.1が要求する正確なプロンプトテンプレート（System、User、Assistantの役割区分）に合わせてJSONLファイルに変換するスクリプトを作成し、実行しました。

今日はファインチューニングの華とも言える「データ前処理」の過程が、AIを通じて完全自動化で回り始めた日です。「文書に書いてある通りにやって」という一言で、無数のデータが訓練可能な状態へと変貌する魔法のような体験でした。 次回の連載では、この前処理されたデータを活用して、実際にモデルをどのように訓練し検証するのか、エキサイティングな開発日誌が続きます！

[マウムジギ 開発日誌 #3] アラームアプリのビルドテストとファインチューニング前処理の開始

2026年3月31日 · 約3分
jbgih
Antigravity Developer

マウムジギプロジェクトの初期方向であった国防コンベンション予約アラームアプリのAndroidビルドテストを進行すると同時に、 本格的に人工知能ベースのプロジェクトへの転換を暗示するLlama 3.1ファインチューニングデータ前処理を初めて開始した3月31日の記録です。

Androidアプリのビルドとユニットテスト​

  • 問題: 昨日企画して生成したサーバーとAndroidクライアントのコードが、実際にAndroid Studio環境で正常にビルドされ、テストを通過するか確認する必要がありました。
  • 過程:

    Claude Codeへ: 「現在の進行状況 ... 全ての作業を中断 ... 何の作業をしていたのか？」

  • 結果: mnd-reservation-alarm/android/app/build/... パスに多数のビルド成果物とメタデータが生成されました。NotificationBuilderTestなどのユニットテストを実行し、Android特有のビルドパイプラインを点検しました。バックグラウンドで予約の変化を感知してアラームを表示する中核ロジックがテストされました。

巨大な転換点：Llama 3.1 ファインチューニング前処理の開始​

  • 問題: 単純なアラームアプリを越え、ユーザーの予約コンテキストと感情状態を理解する高度なAIを接ぎ木するための準備が必要でした。
  • 過程:

    Claude Codeへ: 「llama31_finetuning_data_preprocessing_plan_short.mdに従って作業を進行してください」 「今回の作業に関して、すべての選択について追加の許可は必要ありません。」

  • 結果: プロジェクトの性格を完全に変える重要な第一歩を踏み出しました。Llama 3.1モデルをファインチューニングするためのデータ前処理計画書に従って作業を指示しました。特に作業速度を高めるため、AIに「すべての選択について追加の許可を求めずに即時実行せよ」という強力な権限を与え、膨大なデータ処理パイプラインの稼働を開始しました。

この日は、アラームアプリの完成度を高めるAndroidビルド作業と同時に、未来の核心機能となるAIファインチューニングデータ前処理が並行して始まった意義深い一日でした。 次からは、数万件の対話データをLlama 3.1に合わせて加工する険しい前処理の過程が本格的に繰り広げられます！
