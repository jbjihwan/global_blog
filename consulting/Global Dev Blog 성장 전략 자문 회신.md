## 먼저: 지금 데이터로는 결론을 내리기 이릅니다

측정을 먼저 바로잡고 4\~8주 뒤 다시 보는 것이 아래 모든 추천의 전제입니다. 사이트는 직접 열어보지 못해 자문서의 수치와 설명만 근거로 했습니다.

**한국 10명 / 460 PV는 운영팀 본인 트래픽일 가능성이 매우 높습니다.** 1인당 46 PV인데, 외부 독자가 한 달에 46페이지를 읽는 경우는 드뭅니다. 글을 쓰고 검수하고 배포를 확인하면서 본인 사이트를 여는 패턴과 일치합니다.

- GA4에서 내부 트래픽 규칙(IP 기준)을 정의하고 데이터 필터를 '활성' 상태로 바꾸세요.
- 이 트래픽을 빼면 실제 외부 PV는 약 260 수준이고, 74.4% 참여율도 상당 부분 내려갈 겁니다.
- "고관여 충성 독자층"은 아마 여러분 자신일 겁니다.

**13 PV는 '압도적 조회수'가 아닙니다.** 30일에 13회면 하루 0.4회입니다. GSC 평균 순위도 노출수 없이 보면 착시가 생깁니다. `npm vulnerability` 같은 경쟁 키워드에서 1.0위가 찍혔다면 노출 몇 회에서 나온 값일 가능성이 큽니다. 쿼리별 노출·클릭·CTR을 함께 보시고, 노출 100회 미만 쿼리는 전략 근거에서 빼시길 권합니다.

**21.6초는 '정독'이 아니라 '답을 찾고 나감'입니다.** 문제 해결형 글은 원래 그래서 나쁜 신호는 아닙니다. 다만 몰입도 근거로 쓰시면 안 됩니다.

방향 자체("실무자의 고통이 검색을 끈다")는 일반적으로 맞는 얘기라 버릴 필요는 없습니다. 다만 지금은 확인된 사실이 아니라 가설입니다.

덧붙여, 외부에 보내실 문서라면 "장악·압도적·폭발적·무결점" 같은 표현은 빼고 노출·클릭 절대값으로 쓰시는 게 좋습니다. 숫자는 작은데 형용사가 크면, 읽는 쪽은 나머지 주장까지 할인해서 읽습니다. 개발자 독자도 마찬가지입니다.

## 1. 추천 방향과 우선순위

측정 정비가 0순위이고, 주력 방향은 새 대안 D(R&D를 문제 해결 글로 분해)입니다. 가설 C는 지금 형태로는 비추천합니다.

**0순위: 측정 정비와 언어 정리 (1\~2주).** 내부 트래픽 필터를 적용하고, GSC 쿼리별 노출수와 언어별 성과를 확인합니다. 비용이 거의 들지 않고 이후 모든 판단의 근거가 됩니다.

**1순위: 새 대안 D, R&D를 '문제 해결 글'로 분해하기.** 가설 A·C가 진짜로 노리는 목적(트래픽을 전문성으로 연결)을 가장 직접적으로 푸는 방법입니다. 독자를 R&D 글로 *끌고 가는* 대신, R&D에서 실제로 부딪힌 문제를 검색되는 형태로 *꺼내 오는* 방식입니다.

- 위기 감지 AI에서: "LLM 파이프라인에 넣기 전 PII 마스킹", "극단적 클래스 불균형 분류기의 평가 지표 고르기", "교차검증에서 데이터 누수 막기"(가설 C의 25-Fold 격리를 독립된 글로)
- 예산 감사 AI에서: "조달청·공공데이터 API 대량 수집하며 겪은 문제", "GraphRAG 엔티티 중복 해소"

이런 글은 그 자체로 검색 수요가 있습니다. 본문에 "이 문제를 겪은 프로젝트"로 R&D 시리즈를 링크하면 연결도 자연스럽습니다. 전문성 증명도 "만들었다"가 아니라 "이렇게 풀었다"가 되어 더 설득력이 생깁니다.

**2순위: 가설 A (수정판).** 보안 트랙은 진행하되, "시리즈 런칭"보다 질문 단위의 답변 글로 접근하세요. 탭을 분리해도 되지만 순위에 주는 영향은 작습니다.

**3순위: 가설 B (축소판).** 레포 10개 대신 하나만 만들고, 공식 과제 풀이가 아닌 자체 실습으로 채우세요.

**가설 C는 지금 형태로는 비추천합니다.** npm 경고를 해결하러 온 독자에게 "임상 AI 데이터 누출 25-Fold 격리"는 관련 링크가 아니라 광고로 읽힙니다. 같은 내용을 D처럼 독립된 글로 쓰고, 문맥 링크로 연결하는 편이 맞습니다.

## 2. 질의별 답변

### Q1. 퍼널 연계

먼저 "전환"을 정의하셔야 합니다. R&D 글로 이동하는 건 중간 단계일 뿐입니다. RSS·뉴스레터 구독, GitHub 팔로우, 협업·채용 문의 중 최종 행동을 하나 정해 GA4 주요 이벤트로 잡으세요. 그래야 개선 여부를 알 수 있습니다.

검색으로 들어와 문제를 해결한 독자가 바로 나가는 건 정상입니다. 그래서 "더 많이 이동시키기"보다 "나가기 전에 한 가지만 남기게 하기"가 현실적인 목표입니다. 효과가 큰 순서는 다음과 같습니다.

1. **본문 중간 문맥 링크**: 해당 문제가 R&D에서 실제로 나온 지점에 한 문장을 넣습니다. 배너보다 훨씬 잘 클릭됩니다.
2. **글 하단 저자 박스**: 실명·프로필, 만든 것 2\~3개, 구독 링크 하나를 둡니다. E-E-A-T 신호 역할도 합니다.
3. **프로젝트 허브 페이지**: 시리즈마다 문제·접근·결과·코드를 한 장으로 요약해 두면 문맥 링크의 착지점이 됩니다.
4. **같은 주제의 관련 글 2\~3개**: 보안 글 밑에는 보안 글을 붙입니다.

### Q2. 보안 시리즈 타당성

타당합니다. 다만 근거를 "1.0위"에 두지 말고 경쟁 구조를 보셔야 합니다. `npm audit fix` 류 쿼리에서는 npm·GitHub 공식 문서와 보안 벤더 블로그가 강합니다. 작은 블로그가 이길 수 있는 지점은 **구체성**입니다. 정확한 에러 문구, 특정 어드바이저리, 그리고 여러분이 실제로 쓰는 스택(Docusaurus, 정적 사이트)이 무기입니다.

주제는 검색 수요와 여러분 전문성 적합도를 함께 보고 이렇게 평가합니다.

| 우선순위 | 주제 | 판단 근거 |
| --- | --- | --- |
| 상 | 의존성 경고 실전 롱테일: devDependencies 경고 판단법, `npm audit --omit=dev`, `overrides`로 전이 의존성 강제 업데이트, `npm audit fix --force`가 깨뜨리는 것들 | 이미 1편이 있어 클러스터를 만들기 가장 쉬움 |
| 상 | 화제가 된 어드바이저리·악성 패키지 사건 해설 | `ghsa-…` 같은 ID 쿼리가 이 유형. 트래픽이 짧게 몰렸다 빠지므로 "발표 후 48시간 내 게시" 같은 운영 원칙 필요 |
| 중 | GitHub Pages + Cloudflare 하드닝, 보안 헤더 | 여러분 스택 그대로라 1차 경험이 들어감 |
| 중 | 서명·SBOM (npm provenance, Sigstore) | 검색량은 적지만 권위 측면에서 좋고, 기업 독자라 광고 단가에도 유리 |
| 하 | eBPF 런타임 보안 | 지금 독자·스택과 거리가 멂 |
| 하 | 악성 패키지 난독화 분석 | 보안 벤더가 직접 분석을 내는 영역이라, 원본 분석 없이 쓰면 2차 요약으로 묻힘 |

### Q3. 스탠포드 강의 차별화

"요약"은 이미 상품화된 영역입니다.

- 2026 가을 학기 CS146S가 9월 22일부터 12월 3일까지 진행 중이고, 공식 강의 녹화본은 없습니다 ([heyuan110](https://www.heyuan110.com/posts/ai/2026-09-11-cs146s-fall-2026-follow-along/)).
- 공식 과제 레포는 mihail911 계정으로 공개돼 GitHub 트렌딩에도 올랐습니다 ([aitoolly](https://aitoolly.com/zh/ai-news/article/2026-09-22-stanford-university-cs146s-modern-software-development-course-assignments-surface-on-github-trending)).
- 중국어판 레포([CS146S\_CN](https://www.sourcepulse.org/projects/23319155))와 한국어판도 이미 있습니다.

`cs146s stanford` 같은 이름 검색의 1\~3위는 공식 강의 페이지, 스탠포드 게시판, 공식 GitHub이 가져갈 가능성이 높습니다. 현실적인 목표는 "cs146s lecture 4 notes" 같은 강의 단위 롱테일과 "MCP 서버 직접 만들기" 같은 강의 주제 쿼리입니다.

효과가 큰 킬러 요소는 이 순서입니다.

1. **직접 해본 결과.** 강의의 주장을 실제 도구로 재현해 본 실패담·수치·스크린샷입니다. 다른 요약본이 가장 못 하는 부분입니다.
2. **2026 학기 업데이트.** 기존 글이 2025 기준이라면 바뀐 부분을 표시하고 갱신일을 명시하세요.
3. **강의별 허브 페이지.** "이 문제는 몇 강을 보라"는 식의 지도를 만들어 내부 링크의 중심으로 씁니다.

다이어그램은 있으면 좋지만 순위 요인으로서는 작습니다.

가설 B는 레포 하나에 강의별 폴더를 두는 구성을 권합니다. **공식 과제 풀이 공개는 피하세요.** 학기 중인 수강생이 베낄 수 있고 강사 측과 불편해질 수 있습니다. 강의 주제를 받아 직접 설계한 미니 실습이 더 안전하고 더 차별적입니다.

### Q4. 다국어 전략

분리할 시점은 맞습니다. 다만 "지역별 주제 특화"보다 더 급한 이유가 있습니다.

68편에 9개 언어면 약 600개 URL입니다. 월 사용자 120명대라면 대부분 언어판은 노출이 0일 겁니다. 구글은 AI 번역을 그 자체로 스팸으로 규정하지 않지만, 품질이 낮은 콘텐츠를 AI 번역으로 대량 확장하면 스팸 업데이트나 scaled content abuse 수동 조치 위험이 있다는 입장입니다 ([GSQI](https://www.gsqi.com/marketing-blog/auto-translating-content-google-scaled-content-abuse/), [Search Engine Journal](https://www.searchenginejournal.com/google-removes-robots-txt-guidance-for-blocking-auto-translated-pages/548870)). 애드센스도 사이트 전체를 보기 때문에, 노출 없는 번역 페이지 수백 개는 '가치 낮은 콘텐츠' 판정의 리스크 요인이라고 봅니다. 이 부분은 정책 문구가 아니라 제 판단입니다.

제안드리는 순서입니다.

1. GSC에서 언어 경로별(`/ja/`, `/de/` …)로 최근 3개월 노출을 확인합니다.
2. 노출이 의미 있는 언어만 남기고 나머지는 신규 번역을 중단합니다.
3. Docusaurus는 번역되지 않은 파일을 기본 언어 원문으로 대체해 해당 로케일 경로에 빌드하는 것으로 알고 있습니다. 일부 글만 번역하면 영어 원문 중복 페이지가 생길 수 있으니 확인해 보세요. 그래서 Docusaurus에서는 글별 선택 번역보다 로케일 수 자체를 줄이는 쪽이 깔끔합니다.
4. 영어(기본)와 한국어는 유지합니다. 번체는 실제 검색 노출이 있으니 보안 글 중심으로 유지를 검토합니다.
5. 예산 감사 AI(조달청 데이터)는 본질적으로 한국 독자의 주제라 한국어판이 본판입니다. 영어판은 "공공데이터 GraphRAG 방법론" 관점으로 번역이 아니라 재작성해야 수요가 생깁니다.

### Q5. 애드센스

공식 자격 요건은 직접 소유한 독창적이고 유용한 콘텐츠, 정책 준수, 18세 이상, 사이트 관리 권한이며 트래픽 기준은 없습니다 ([theguidex](https://theguidex.com/resources/google-adsense-approval)). 이 사이트의 리스크는 트래픽이 아니라 세 가지입니다.

- 대량 번역 페이지
- 원문을 따라가는 강의 요약
- 흐릿한 저자 정체

재심사 전에 Q4 정리를 마치고, 강의 글에 해설·실습 비중을 늘리고, About 페이지에 실명·경력·GitHub를 명시하세요.

수익 기대치는 현실적으로 잡으셔야 합니다. 720 PV에 기술 블로그로서 낙관적인 RPM $5\~$20을 가정해도 월 $4\~$14 정도입니다. 내부 트래픽을 빼면 그 3분의 1 남짓입니다. 지금 단계에서는 애드센스가 의사결정을 끌고 가면 안 됩니다. 개발자 독자는 광고에 민감해서, 광고 밀도가 성장 자체를 깎을 수 있습니다.

승인 이후에는 이렇게 하시길 권합니다.

- **밀도:** 본문 내 광고는 1\~2개로 제한합니다.
- **위치:** 코드 블록과 복사 버튼 옆은 피합니다. 실수 클릭이 생기면 무효 클릭 정책 리스크가 됩니다.
- **위기 감지 AI 글:** 광고를 빼시길 권합니다. 정책상 금지 예시는 자살·자해를 옹호하는 콘텐츠라 감지 연구 글이 위반은 아닙니다 ([Google Publisher Policies](https://support.google.com/publisherpolicies/answer/10502938?authuser=0)). 하지만 위기 관련 검색으로 들어올 수 있는 페이지에 광고가 붙으면 독자 신뢰 손실이 더 큽니다. 자동 광고의 페이지 제외 기능으로 처리하면 됩니다.
- **고단가 주제:** 높은 RPM은 영어권 트래픽과 B2B 주제(보안 도구, 클라우드)에서 나옵니다. Q2의 서명·SBOM 쪽이 여기 해당합니다.

## 3. 반드시 피해야 할 함정

1. **작은 표본으로 큰 결정 내리기.** 쿼리당 노출 수백 단위가 쌓이기 전까지는 방향 신호로만 쓰세요.
2. **번역·AI 생성으로 양 늘리기.** 9개 언어 일괄 번역이 이미 이 방향에 가깝습니다.
3. **과장된 문체.** 개발자 독자는 큰 형용사에서 먼저 이탈합니다. 결과는 숫자로 쓰고 한계는 명시하세요.
4. **민감 주제의 무게를 가볍게 보기.** 위기 감지 글은 YMYL에 가까워 품질 평가가 엄격하고, 실제 위기에 있는 독자가 읽을 수 있습니다. 방법 관련 세부 묘사를 피하고, 위기 상담 안내(국내 109)를 넣고, "임상"이라는 표현은 실제 검증한 범위 안에서만 쓰세요.
5. **도메인 권위(DA)를 목표로 삼기.** DA는 서드파티 지표이지 구글 순위 요소가 아닙니다. 목표 지표는 GSC 노출·클릭과 Q1에서 정한 전환 이벤트로 두세요.
