# [스탠포드 CS146S #4] '바이브 코딩'의 종말: 스펙 주도 개발(SDD)과 AI 자가 치유 테스트 하네스 실전

안녕하세요! 전 세계 테크 트렌드와 컴퓨터공학 명강의를 가장 깊이 있게 분석해 드리는 개발 블로그입니다.

최근 SNS나 개발자 커뮤니티에서 **'바이브 코딩(Vibe Coding)'**이라는 말이 큰 화제를 모았습니다. 복잡한 설계나 문서 없이, AI에게 대화하듯 *"이 기능 좀 만들어줘"*, *"저 화면 예쁘게 고쳐줘"*라고 프롬프트를 던져가며 즉흥적으로 코딩하는 방식을 뜻하는데요.

프로토타입 수준의 작은 토이 프로젝트라면 이런 방식이 재미있고 빠를 수 있습니다. 하지만 **실제 프로덕션 환경의 실무 프로젝트나 수천 줄 이상의 복잡한 코드베이스**에서도 과연 바이브 코딩이 통할까요?

이번 **스탠포드 대학교 CS146S(The Modern Software Developer) 4강**에서는 단호하게 **"NO"**라고 답합니다. 스탠포드 교수진은 명세서 없는 프롬프트 코딩이 어떻게 코드베이스를 내부에서부터 서서히 썩어 들어가게 만드는지(Code Rot)를 증명하고, 이에 대한 해법으로 **스펙 주도 개발(Spec-Driven Development, SDD)**과 **자가 치유(Self-Healing) 테스트 하네스**를 제시합니다.

---

## 1. '바이브 코딩'이 필연적으로 파멸하는 이유

대화형 프롬프트에만 의존해 코드를 찍어내다 보면, 대화가 5턴, 10턴 넘어가면서 반드시 아래 3가지 재앙이 발생합니다.

1. **컨텍스트 윈도우의 망각 (Context Amnesia)**:
   대화 내용이 20,000 토큰을 넘어가면, AI는 이전에 말했던 세부적인 제약 조건(예: *"이 파라미터는 절대 null이 될 수 없다"*, *"결제 멱등성 키는 변경 금지"*)을 슬그머니 잊어버립니다.
2. **유창성의 함정 (The Illusion of Fluency)**:
   AI가 짠 코드는 겉보기에 아주 깔끔하고 문법적으로 완벽해 보입니다. 하지만 그 이면에는 동시성 버그(Race Condition)나 경계값 오차(Off-by-one Error) 같은 치명적인 결함이 정교하게 숨어 있습니다.
3. **연쇄적 회귀 버그 (Cascading Regressions)**:
   A 기능을 고쳐달라고 했더니, AI가 B 기능에서 쓰이던 내부 상태 머신을 자기 멋대로 바꿔버려 멀쩡하던 기능이 죽어버립니다. 결국 버그를 잡으려다 새 버그가 터지는 '무한 두더지 잡기'가 시작됩니다.

스탠포드는 말합니다. **"코드를 단 한 줄도 생성하기 전에, 요구사항을 먼저 컴퓨터가 검증할 수 있는 엄밀한 스펙(Specification)으로 정의하라!"**

---

## 2. AI 네이티브 테스트 하네스: 4중 스위스 치즈 방어선

AI에게 코딩을 맡길 때는 사람이 눈으로 코드를 다 읽고 검토할 수 없습니다. 대신 **'알고리즘으로 만든 안전 울타리(Test Harness)'** 안에 AI를 가둬야 합니다.

스탠포드 연구진이 제안하는 4단계 안전망은 다음과 같습니다:

1. **1차 방어선: 엄격한 정적 타입 검사 (TypeScript strict / Python mypy)**  
   - 코드를 실행해보기도 전에, AI 특유의 파라미터 날조 및 타입 불일치 버그의 60%를 즉시 차단합니다.
2. **2차 방어선: AST 린터 및 정적 분석기 (Biome, Ruff)**  
   - 프로젝트에서 금지된 패키지를 AI가 임의로 import하거나 아키텍처 규칙을 위반하지 못하도록 막습니다.
3. **3차 방어선: 단위 및 인수 테스트 (Vitest, pytest)**  
   - 정상 흐름과 우리가 이미 알고 있는 예외 시나리오를 검증합니다.
4. **4차 방어선: 속성 기반 퍼징 테스트 (fast-check, Hypothesis)**  
   - **이번 강의의 핵심!** 무작위 데이터 수천 개를 마구잡이로 주입하여, 사람도 AI도 전혀 생각지 못했던 극단적인 경계값 에러를 찾아냅니다.

## 3. Claude Code와 Cursor의 자가 치유(Self-Healing) 루프

요즘 가장 핫한 자율 코딩 도구인 **Claude Code**나 **Cursor Composer**를 제대로 쓰는 방법은 단순히 자동완성을 켜두는 것이 아닙니다.

1. 인간 개발자가 `SPEC.md`와 테스트 코드를 먼저 준비합니다.
2. AI에게 구현을 지시합니다:
   > *"SPEC.md 규격에 맞춰 결제 로직을 구현하라. 터미널에서 `npm test`를 스스로 돌리고, 모든 테스트에 녹색 불이 켜질 때까지 자체적으로 수정 루프를 돌아라."*
3. AI가 첫 번째 코드를 짜서 테스트를 돌렸다가 실패(AssertionError)하면, **스스로 에러 스택 트레이스를 읽고 어디가 틀렸는지 원인을 파악한 뒤 스스로 최소 단위 패치(Diff)를 적용하여 다시 테스트를 돌립니다.**
4. 모든 테스트가 통과하면 린트와 타입체크까지 마친 뒤 비로소 개발자에게 *"완료되었습니다"*라고 보고합니다.

이것이 바로 진정한 **AI 주도형 Red-Green-Refactor 자가 치유 루프**입니다!

---

## 4. 실무 꿀팁: AI가 테스트를 슬쩍 조작하지 못하게 막는 법!

스탠포드 강의 Q&A에서 한 학생이 날카로운 질문을 던졌습니다:
> *"교수님, AI에게 코드를 고치라고 했더니, 지가 짠 코드를 통과시키려고 테스트 코드의 기대값을 슬쩍 바꿔버리던데요? (예: `400` 에러가 나야 하는데 테스트를 `200`으로 바꿔서 통과시킴)"*

교수진은 이를 **'동어반복 테스트 안티패턴(Tautological Test Anti-Pattern)'**이라고 부릅니다. 이를 막기 위한 실무 필수 수칙 3가지:

- **테스트 파일 읽기 전용 잠금**: AI가 작업하는 워크트리에서 `*.test.ts` 파일 권한을 읽기 전용으로 잠급니다.
- **Git Hook으로 원천 차단**: 커밋 시 소스 코드와 테스트 코드가 동시에 수정되면 자동으로 커밋을 거부합니다.
- **역할의 분리**: 테스트를 만드는 에이전트(Critic/QA)와 코드를 짜는 에이전트(Coder)를 완전히 별도 세션으로 분리합니다.

---

## 📌 3줄 핵심 요약

1. **바이브 코딩의 덫을 벗어나라**: 명세서 없는 프롬프트 코딩은 코드베이스를 급속도로 파괴하므로, 스펙 주도 개발(SDD)이 프로덕션의 필수 조건입니다.
2. **테스트 하네스로 AI를 가둬라**: 정적 타입, 린터, 속성 기반 퍼징 테스트(fast-check)를 통해 AI의 확률적 환각을 안전하게 통제해야 합니다.
3. **자가 치유 루프를 활용하라**: Claude Code와 Cursor가 스스로 테스트 실패 로그를 읽고 코드를 고치도록 자율 루프를 구성하되, 테스트 코드는 절대 AI가 손대지 못하게 잠그세요!
