# [AI 실전] 국가 예산 650조를 감사하는 AI 에이전트 개발기: 예상한 난제와 실제 버그 해결법

안녕하세요! 오늘은 최근 저희 팀이 집중적으로 구축한 **"대한민국 국가 예산 전주기 추적 및 부정수급 탐지 AI 시스템"** 개발기를 공유해 드리고자 합니다.

연간 650조 원이 넘는 국가 예산과 조달청 나라장터의 수만 건의 계약 데이터, 그리고 복잡하게 얽힌 HWP 산출내역서를 다루면서 **설계 단계에서 예상했던 어려운 점을 어떻게 예방했고, 실제 구현 과정에서 마주친 예상 밖의 오류들을 어떻게 해결했는지** 생생하게 기록해 보았습니다.

---

## 📌 한눈에 보는 핵심 요약 (TL;DR)

1. **목표**: 나라장터(KONEPS), 열린재정(dBrain+), 비정형 HWP 예산서를 연계하여 **과대계상, 쪼개기 수의계약, 페이퍼컴퍼니 담합**을 적발하는 자율 감사 AI 에이전트 개발.
2. **사전 예방**: LLM의 치명적 단점인 수치 계산 환각을 막기 위해 **결정론적 Text-to-SQL**을, 복잡한 이해관계망 추적을 위해 **지식 그래프(GraphRAG)**를 채택하는 이원화(Dual-Engine) 구조 사전 설계.
3. **실제 마주친 오류 해결**:
   - 상호명과 도로명 주소 표기 파편화로 인한 카르텔 추적 실패 ➔ **EntityResolver 정규화 엔진**으로 해결.
   - 시간차를 두고 발주하는 쪼개기 계약 누락 ➔ **슬라이딩 윈도우(Sliding Window)** 알고리즘으로 해결.
   - AI 점수에 대한 법적 증거력 불신 ➔ **국가계약법/감사원 10개년 판례 1:1 매칭 XAI Dossier** 탑재.
4. **검증 결과**: 11개 단위·통합 테스트 전원 PASS, 3,850만 원 규모 동일 주소지 담합 적발 성공.

## 1. 왜 단순 프롬프트(Vibe-Coding)로는 감사를 할 수 없는가?

요즘 LLM의 발전으로 프롬프트 몇 줄로 코드를 짜거나 문서를 요약하는 경우가 많습니다. 하지만 1원의 오차도 법적 분쟁으로 번질 수 있는 **공공 재정 감사(Public Audit)** 영역에서는 단순 프롬프트 기반 접근이 100% 실패합니다.

- **수치 계산의 비결정성**: LLM에게 계약 금액 합계를 물어보면 매번 다른 숫자를 내놓거나 자릿수를 틀리는 환각(Hallucination)이 발생합니다.
- **다단계 은폐 수법**: 부패 카르텔은 2천만 원 이하 수의계약 한도를 노려 페이퍼컴퍼니 여러 개로 쪼개서 계약하기 때문에, 일반적인 DB 단일 테이블 필터링으로는 정상 계약처럼 보입니다.

따라서 우리는 **스펙 주도 개발(Spec-Driven Development)** 원칙에 입각하여 시스템을 철저히 모듈화했습니다.

## 2. 개발 전 '예상했던 3대 난제'와 사전 예방책

### ① LLM의 수치 계산 환각 위험 ➔ 결정론적 Text-to-SQL
- **예방 설계**: LLM에게 숫자를 계산시키지 않고, 사용자의 자연어 질문을 **엄격한 SQL 문으로 번역하는 역할**만 맡겼습니다.
- 실제 계산과 순위 산출은 격리된 SQLite/DuckDB 엔진이 처리하므로 계산 오류가 **0%**로 보장됩니다.

### ② HWP 공공문서의 복잡한 표 병합 ➔ 가상 2D 그리드 복원기
- **예방 설계**: 공공 예산서는 HWP 표 안에 병합 셀(Rowspan/Colspan)과 `단가 × 수량 = 총액` 식들이 얽혀 있습니다. 가상 2D 매트릭스로 셀 좌표를 복원하고, 정규식 검증으로 단가와 총액의 일치성을 검사했습니다.

### ③ 관계망 은폐 ➔ 이종 지식 그래프(GraphRAG)
- **예방 설계**: 발주기관, 계약, 기업, 대표자, 본점 주소지를 각각 노드로 정의하고 네트워크를 순회(Graph Traversal)할 수 있는 NetworkX 기반 지식 그래프 엔진을 사전 구축했습니다.

## 3. 실제 개발 중 마주친 '3대 돌발 오류'와 치열한 해결기

아무리 사전에 철저히 설계했더라도, 실제 공공 데이터를 밀어 넣자마자 예상치 못한 버그들이 쏟아졌습니다.

### 🚨 버그 1: 상호명과 도로명 주소 파편화로 카르텔 탐색 실패
- **증상**: 나라장터 계약서에 `(주)대한소프트`, `주식회사 대한 소프트`, `대한소프트(유)` 등으로 기업명이 제각각 적혀 있었고, 주소지도 `테헤란로 152 4층` vs `테헤란로 152, 401호`로 등록되어 있었습니다.
- **결과**: 지식 그래프에서 서로 다른 별개 노드로 인식되어, 한 건물에서 3개 유령 법인을 돌리며 3,850만 원을 독점 수주한 카르텔을 그래프가 완전히 놓쳤습니다 (탐지율 0%).
- **해결책**:
  - `EntityResolver` 모듈을 만들어 법인격 접두/접미사 및 공백을 완벽 제거했습니다.
  - 주소지는 층/호수를 정규식으로 분리하고 **[시/도 + 도로명 + 건물번호]까지만 묶는 `base_address` 정규화**를 적용했습니다.
  - 적용 즉시 카르텔 탐지율이 **100%**로 복구되었습니다!

### 🚨 버그 2: 시간차 쪼개기(Temporal Smurfing) 계약 누락
- **증상**: 처음에는 같은 날짜에 발주된 건만 쪼개기 계약으로 탐지하도록 짰습니다. 하지만 지능적인 업자들은 월요일에 1,950만 원, 목요일에 1,900만 원으로 날짜를 벌려 계약했습니다.
- **해결책**:
  - 정적 일자 필터링을 버리고 **7일 / 30일 슬라이딩 타임 윈도우(Sliding Window)** 알고리즘을 도입했습니다.
  - 타임스탬프 기준으로 누적 수주액이 2,000만 원 한도를 넘어서는 패턴을 완벽히 포착해 냈습니다.

### 🚨 버그 3: AI 점수(Score)에 대한 감사관들의 불신
- **증상**: 프로토타입 시연에서 AI가 "이상 위험도 92점"이라고 표시하자, 감사관과 법률팀은 "구체적으로 법 몇 조를 어겼는지 증거가 없으면 감사 보고서로 쓸 수 없다"고 지적했습니다.
- **해결책**:
  - `AuditReporter`와 `CaseMatcher`를 구현했습니다.
  - 국가계약법 시행령 제68조(분할계약 금지), 보조금관리법 제26조의2를 1:1 매핑하고, 감사원(BAI) 10개년 공식 감사 지적 사례와 코사인 유사도 94.5%로 매칭하는 **정식 감사 Dossier 포맷**을 완성했습니다.

## 5. 개발을 마치며: 엔지니어가 가져야 할 교훈

이번 프로젝트를 완성하면서 얻은 가장 중요한 원칙은 **"AI를 전지전능한 마법사로 취급하지 말고, 엄격한 스펙과 가드레일 안에 가두는 시스템 엔지니어가 되어야 한다"**는 점이었습니다.

1. **숫자는 DB에 맡긴다**: LLM에게 계산을 시키지 말고 SQL 생성만 맡겨야 오차가 없습니다.
2. **현실 데이터는 항상 불완전하다**: 상호명과 주소 정규화(Entity Resolution)가 AI 파이프라인의 성패를 가릅니다.
3. **설명 가능성이 법적 효력을 만든다**: AI의 추상적인 점수가 아니라, 관련 법령과 공인된 감사 판례를 1:1로 증거 바인딩해야 실제 실무에서 채택됩니다.
