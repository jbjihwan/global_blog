[마음지기 캡스톤 개발일지 #13] 70B 학습의 한계와 중소형 모델(HCX, Qwen) 우회 전략

2026년 5월 4일 · 약 2분
jbgih
Antigravity Developer

70B라는 거대한 모델의 파인튜닝 과정에서 발생한 OOM(메모리 부족) 지옥을 경험한 5월 4일, 저희는 과감한 전략 변경을 시도했습니다. 70B 모델(Llama3.3, DeepSeek-R1)은 배치 사이즈를 극단적으로 줄여 겨우 checkpoint-1200, 1300까지 진행시켰지만, 학습 시간이 너무 오래 걸려 효율이 극악이었습니다.

중소형 모델(1.5B ~ 9B)로 눈을 돌리다​

물리적인 서버 자원과 캡스톤 프로젝트의 마감 기한을 고려했을 때, 70B에만 매달리는 것은 위험하다고 판단했습니다. 그래서 HCX-Omni-8B, Qwen35-9B, HCX-Text-1.5B 와 같은 상대적으로 가벼운 중소형 모델들로 파인튜닝 대상을 선회하여 실험을 시작했습니다.

"현재 지정한 하이퍼파라미터로 HCX-Omni-8B, Qwen35-9B, HCX-Text-1p5B를 학습시키는데 시간이 오래 걸리는데, 보편적으로 모델별로 이러한 파라미터가 사용되는가?" "이 batch size 상향이 학습에 어떠한 영향을 미치나요?"

작은 모델이라고 해서 모든 것이 순조로운 것은 아니었습니다. 빠른 학습을 위해 배치 사이즈(Batch Size)를 상향 조정해 보고, 모델 크기에 맞는 하이퍼파라미터 최적화 값을 찾아 AI와 끝없는 토론을 이어갔습니다. 가장 작은 모델인 HCX-Text-1.5B의 학습 결과를 먼저 뽑아내어 성능 평가를 진행하며 튜닝의 방향성을 잡아나갔습니다.

체크포인트 저장 오류와 커널 버전 문제​

HCX-Omni-8B 학습을 순조롭게 진행하던 중, 50 스텝에서 체크포인트를 저장하려다 또 다른 암초를 만났습니다.

[RANK 0] Detected kernel version 5.4.0, which is below the recommended minimum of 5.5.0; this can cause the process to hang.
...
![사진 02](./images/02_error.png)

JSONDecodeError Traceback (most recent call last)
---> 60 trainer.train(resume_from_checkpoint=...)

운영체제의 커널 버전이 낮아 프로세스가 멈출 수 있다는 경고와 함께, 저장된 체크포인트의 JSON 파일이 깨져서(JSONDecodeError) 학습을 재개하지 못하는 끔찍한 에러였습니다.

"현재 모델들이 학습 중 중단되면 중단된 부분에서 다시 학습을 시작하나요?"

다행히 허깅페이스 Trainer는 체크포인트부터 이어서 학습(resume_from_checkpoint)하는 기능을 제공하지만, 그 체크포인트 파일 자체가 손상되면 말짱 도루묵이 됩니다. 모델 크기를 줄였음에도 여전히 프레임워크와 인프라 단에서 발생하는 수많은 에러들과 씨름하며 하루를 꼬박 보냈습니다. 과연 안정적인 학습 궤도에 오를 수 있을까요?

[마음지기 캡스톤 개발일지 #12] 70B 초대형 모델 파인튜닝과 GPU 메모리(OOM) 사투

2026년 5월 3일 · 약 2분
jbgih
Antigravity Developer

5월 3일, 그동안 8B 모델로 충분히 감을 잡은 저희 팀은 드디어 진정한 성능의 끝판왕, 70B(700억 개 매개변수) 초대형 모델의 파인튜닝에 도전했습니다. Llama 3.3 70B와 DeepSeek-R1 70B 두 가지 모델을 대상으로 학습을 시도했는데, 예상대로 엄청난 하드웨어 자원의 장벽에 부딪히고 말았습니다.

70B 모델, 그리고 OOM(Out of Memory)의 공포​

  • 문제: 호기롭게 서버에 70B 파인튜닝 코드를 올리고 실행하자마자 오류가 터져 나오기 시작했습니다.
  • 과정:

    "서버의 fine_tuning 폴더와 하위 파일을 복사했습니다. 복사한 파일 확인 후 오류 원인을 파악해 줘." "DeepSeek의 70B 모델은 수정하지 않아도 되나? 오류 가능성 확인 바람."

  • 결과: train_log.jsonl을 분석하며 남은 예상 소요 시간을 묻는 여유도 잠시, 70B 모델이 GPU 메모리를 순식간에 집어삼켜버렸습니다. (OOM 에러 발생!)

GPU 메모리 다이어트 작전​

  • 문제: "이미 GPU memory의 사용량은 MAX이다." 어떻게든 메모리 사용량을 줄여야 학습이 멈추지 않고 돌아갈 수 있었습니다.
  • 과정:

    "save_steps = 50, save_total_limit = 10, eval_steps = 50, patience = 10 으로 수정." "설정한 early stopping 조건에 대해 평가 바람." "ft_configs.yaml에서 70B 두 모델의 max_seq_length를 512로 설정했으나 서버 nvitop에서는 여전히 memory가 max로 사용됩니다. 왜 그런가?"

  • 결과: 한 번에 처리하는 문맥의 길이(max_seq_length)를 512로 과감하게 줄이고, 불필요한 저장을 줄이기 위해 하이퍼파라미터를 대폭 수정했습니다. 하지만 nvitop으로 모니터링해보니 여전히 VRAM은 한계치에 달해 헐떡이고 있었습니다. 급기야 스텝 100, 150 부근에서 계속 멈춰버리는 끔찍한 현상이 반복되었습니다.

70B라는 거대한 짐승을 길들이는 것은 정말 쉽지 않습니다. AI에게 끝없이 에러 로그를 던져주며 해결책을 찾고 있지만, 물리적인 VRAM 한계를 소프트웨어 최적화 기법(LoRA, 퀀타이제이션 등)으로 극복할 수 있을지 끝없는 테스트가 필요해 보입니다. 과연 우리는 70B 모델 파인튜닝에 성공할 수 있을까요? 다음 일지에서 계속됩니다!

[마음지기 캡스톤 개발일지 #11] 합성 데이터(v5) 훈련 결과 M6 모델 평가

2026년 4월 19일 · 약 2분
jbgih
Antigravity Developer

4월 19일, 피땀 흘려 만들어낸 가상의 합성 데이터셋(v5)으로 훈련시킨 모델(M6)의 성능을 평가하고, 이를 바탕으로 7주 차 주간 보고서를 작성한 날입니다. 과연 10달러의 과금 폭탄을 견뎌내며 만들어낸 데이터는 그만한 가치가 있었을까요?

모델 성능 진검승부: M0 vs M5 vs M6​

  • 문제: 지도교수님과 팀원들을 설득하기 위해, 단순히 "좋아졌다"가 아니라 정량적인 테스트 결과와 직관적인 비교 예시가 포함된 주간 보고서가 필요했습니다.
  • 과정:

    "보고서 재작성 바람. 주요 포인트는 v4를 기반으로 한 M5와 v5를 기반으로 한 M6의 비교이다... 각 데이터셋의 예시를 포함하여 작성 바람." "테스트 결과에 대해 서술할 때 튜닝 전 기본 모델(M0)과 M6의 차이도 예시를 든 설명을 포함해 줘."

  • 결과: AI가 M0, M5, M6 모델이 생성한 텍스트 결과를 분석하여 비교 파일을 추출(m0_m6_compare.json)했습니다. 그 결과, 기본 Llama 3.1 모델(M0)은 한국어 상담에 다소 어색한 모습을 보였고, 정제 데이터(v4)로 학습한 M5는 나아졌지만 깊이가 부족했던 반면, 고품질 합성 데이터(v5)로 학습한 M6 모델은 사용자의 감정에 깊이 공감하는 심리상담사 특유의 따뜻하고 전문적인 어투를 완벽하게 구사해 냈습니다.

AI가 대신 써주는 7주 차 주간 보고서 (DOCX)​

  • 과정:

    "결과와 의의를 중점으로 7주 차 보고서를 두 버전(5장 이내 간결 버전, 상세 버전)으로 작성해 주세요. 그리고 두 md를 기반으로 각각 docx 파일을 생성해 줘."

  • 결과: 지시 한 번에 7주차_보고서_v1_간결.md, 7주차_보고서_v2_상세.md 두 가지 버전이 뚝딱 완성되었고, 깔끔하게 워드 파일로 변환까지 완료되었습니다.

RAG 아키텍처 도입: FAISS DB 구축 평가​

  • 과정:

    "FAISS_DB_구축을 수행하고 FAISS_DB_구축_보고서.docx를 작성했습니다. 우리의 계획과 해당 보고서 결과에 대해 평가해 주세요."

  • 결과: 단순히 모델의 가중치를 깎는 파인튜닝뿐만 아니라, 외부 지식을 참조하여 할루시네이션(환각)을 줄이는 RAG(검색 증강 생성) 기법을 위해 FAISS 벡터 데이터베이스를 도입했습니다. AI에게 제가 구축한 구조를 평가해 달라고 요청했고, 긍정적인 피드백(FAISS_DB_구축_평가.md)을 받았습니다.

오늘은 그동안의 고생이 빛을 발한 날이었습니다. 훈련시킨 AI 모델이 정말로 눈에 띄게 똑똑해진 것을 확인했을 때의 그 짜릿함이란! 모델 성능도 입증했고, FAISS DB까지 성공적으로 연동되었으니 마음지기 챗봇이 완성에 한 걸음 더 가까워졌습니다.

[마음지기 캡스톤 개발일지 #10] API 제한 해제와 데이터 합성의 재개

Antigravity Developer

4월 14일, 요금 폭탄 사태 이후 잠시 중단되었던 합성 데이터(v5) 생성 작업을 다시 재개한 날입니다. API 요금 한도를 상향(제한 해제)하고 시스템을 돌렸지만, 이번에도 역시 순탄하게 넘어가진 않았습니다.

"API 제한 해제 완료, 이어서 작동 바람!"​

  • 문제: 지난번 대규모 데이터 생성 시도 때 월별 API 한도를 초과하여 스크립트가 강제 중단되었던 상태였습니다.
  • 과정:

    "v5_emotion_data_generation_commands.md에 따라 작업 진행" "API 제한 해제 완료, 이어서 작동 바람" (23시 32분) "API 제한 해제 완료, 이어서 작동 바람" (00시 11분)

  • 결과: Claude API 콘솔에 접속하여 결제 한도를 과감하게 늘리고 제한을 풀었습니다. AI에게 중단되었던 지점부터 이어서 데이터를 생성하라고 거듭 지시하며 파이프라인을 재가동했습니다.

고장 난 파이프라인 수리와 무인 자동화​

  • 문제: API 제한은 풀렸지만 어찌 된 일인지 새로운 데이터가 정상적으로 만들어지지 않고 있었습니다.
  • 과정:

    "아무것도 생성되지 않습니다. 확인 바람" "작업이 완료되면 결과물 확인 후 자동으로 API 연결 해제 (관련 권한 모두 허락하므로 권한 허락받을 필요 없음)"

  • 결과: 생성 로직 중간에 발생한 꼬임을 AI가 스스로 확인하고 수정(v5_sync_progress.json 추적)하도록 조치했습니다. 매번 옆에서 에러를 고치며 지켜볼 수 없었기에, 아예 "모든 권한을 줄 테니 작업이 끝나면 알아서 API 연결을 끊고 안전하게 종료하라"는 무인 자동화 지시를 내렸습니다.

오늘은 데이터 전처리를 위해 돈(API 요금)과 시간, 그리고 자동화 스크립트라는 삼박자를 맞춰가는 험난한 여정이었습니다. 무사히 데이터 생성이 완료되면 드디어 다음 단계로 나아갈 수 있겠죠? 다음 개발일지에서 뵙겠습니다!

[마음지기 캡스톤 개발일지 #9] Llama 3.1 파인튜닝 에러 사투와 6주차 중간발표

2026년 4월 9일 · 약 2분
jbgih
Antigravity Developer

4월 9일, 어제 야심 차게 완성한 Colab 노트북을 이용해 드디어 인공지능 모델(Llama 3.1)의 첫 학습(파인튜닝)을 시도했습니다. 하지만 현실은 역시 호락호락하지 않았고 수많은 에러와 마주해야 했습니다. 동시에 캡스톤 디자인 6주차 중간발표 자료까지 만들어야 했던 험난한 하루였습니다.

Colab 파인튜닝 에러와의 끝없는 사투​

  • 문제: 어제 만든 llama31_finetuning_colab.ipynb를 실행하자마자 각종 에러가 쏟아졌습니다.
  • 과정:

    "llama31_finetuning_colab (3).ipynb에서 M1 파인튜닝 진행 중 오류가 발생한 이유가 무엇일까요?" "실행한 결과에 eos_token이 포함되어 있습니다. 왜 이런 문제가 발생할까요?"

    "이미 Pro 구독으로 Claude를 사용 중인데 API가 별도로 필요하나요?" "Anthropic API가 아닌 Claude Code를 사용하는 방법은 없나요? 과금이 부담스럽습니다." "실제 비용은 10.27 달러가 나왔습니다."

  • 결과: Claude Pro 구독(월 20달러)과는 별개로, 파이썬 스크립트에서 자동화로 대량의 데이터를 처리하기 위해 호출하는 Anthropic API는 사용량만큼 종량제로 과금된다는 뼈아픈 사실을 체감했습니다. 단 10만 줄을 테스트로 처리하는 데에만 순식간에 약 14,000원($10.27)이 과금되었습니다. 100만 건을 모두 처리하려면 엄청난 비용이 든다는 것을 깨닫고, 모델 최적화와 데이터 샘플링의 중요성을 몸소 배운 하루였습니다.

오늘은 딥러닝 데이터 전처리 과정에서 필연적으로 마주하게 되는 '컴퓨팅 비용'이라는 현실적인 장벽에 부딪힌 날이었습니다. 결과적으로 정제된 양질의 데이터(v4_report.md)를 얻어내는 데는 성공했지만, 앞으로 어떻게 이 비용과 효율성의 균형을 맞추며 파인튜닝을 진행할지 깊은 고민을 안겨준 소중한 경험이었습니다!

[마음지기 캡스톤 개발일지 #4] 파인튜닝 데이터 전처리 본격 가동

2026년 4월 1일 · 약 2분
jbgih
Antigravity Developer

마음지기 프로젝트의 핵심 엔진이 될 Llama 3.1 모델을 훈련시키기 위해, 방대한 양의 대화 데이터를 모델이 학습할 수 있는 형식으로 가공하기 시작한 4월 1일의 기록입니다.

데이터 전처리 계획에 따른 자동화 실행​

  • 문제: 모델을 파인튜닝하기 위해서는 사용자의 발화와 챗봇의 응답이 담긴 원시 데이터를 Llama 3.1이 이해할 수 있는 특수한 JSONL 형식으로 완벽하게 변환해야 했습니다.
  • 과정:

    Claude Code에게: "llama31_finetuning_data_preprocessing_plan_short.md에 따라서 작업 진행"

  • 결과: 어제 작성한 전처리 계획서(llama31_finetuning_data_preprocessing_plan_short.md)를 바탕으로 AI 에이전트가 데이터 정제 및 가공 파이프라인을 스스로 구축하고 실행하기 시작했습니다. 사람이 직접 수만 건의 데이터를 일일이 변환하는 대신, 규칙이 적힌 마크다운 문서 하나를 던져주며 "이대로 처리해"라고 지시하는 방식입니다.

카테고리 데이터 통합 및 JSONL 변환​

  • 문제: 전처리 과정은 여러 단계(Step)로 쪼개져 있었고, 최종적으로 모든 데이터를 하나로 합쳐서 훈련용 데이터셋을 완성해야 했습니다.
  • 과정:

    Claude Code에게: "Step 4를 실행해. 두 카테고리 데이터를 통합해서 Llama 3.1 JSONL 형식으로 변환해."

  • 결과: AI가 즉각적으로 Step 4를 수행하여 흩어져 있던 각 카테고리의 대화 데이터를 하나로 병합했습니다. 그리고 Llama 3.1이 요구하는 정확한 프롬프트 템플릿(System, User, Assistant 역할 구분)에 맞추어 JSONL 파일로 변환하는 스크립트를 작성하고 실행했습니다.

오늘은 파인튜닝의 꽃이라고 할 수 있는 '데이터 전처리' 과정이 AI를 통해 완전 자동화로 돌아가기 시작한 날입니다. "문서에 적힌 대로 알아서 해"라는 말 한마디로 수많은 데이터가 훈련 가능한 상태로 탈바꿈하는 마법 같은 경험이었습니다. 다음 연재에서는 이 전처리된 데이터들을 활용해 실제로 모델을 어떻게 훈련시키고 검증하는지, 흥미진진한 개발일지가 이어집니다!
