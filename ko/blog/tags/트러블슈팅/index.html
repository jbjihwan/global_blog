[마음지기 캡스톤 개발일지 #19] 파인튜닝 보고서 자동화와 백엔드 데이터베이스(DB) 연동 트러블슈팅

2026년 5월 17일 · 약 2분
jbgih
Antigravity Developer

제가 이전에 "5월 13일이 마음지기 5월 개발의 마지막일 것"이라고 착각했던 것을 정정합니다! 5월 17일, 어마어마한 양의 백엔드 연동 테스트와 보고서 작업이 몰아쳤습니다.

인공지능(AI)를 활용한 파인튜닝 결과 보고서 자동화​

2차 파인튜닝(fine_tuning_2)의 방대한 결과 그래프(common, daily 데이터셋 비교 등)를 하나씩 사람이 분석해서 쓰기에는 시간이 너무 부족했습니다.

"모델들의 추론 결과를 비교하는 보고서를 작성하기 위한 프롬프트를 만들어주세요. 프롬프트 자체를 report_prompt.md로 저장하고, 이에 따라 보고서 작성을 수행해 줘." "내가 바란 보고서는 .md 형식이 아닌 .docx 형식을 희망했습니다."

AI에게 결과 지표를 해석하게 하고, 보고서 초안을 자동으로 작성하는 프롬프트 엔지니어링을 시도했습니다. 결과적으로 AI가 각 모델의 장단점과 Alpha 값에 따른 차이를 분석해 훌륭한 워드(.docx) 보고서 초안을 뽑아주었습니다.

백엔드 DB 연동과 401 Unauthorized의 늪​

보고서가 마무리되자마자 프론트엔드와 백엔드의 시스템 안정성을 테스트하기 위해 backup.sql 데이터를 로컬 PostgreSQL DB에 밀어 넣는 작업을 시작했습니다.

"backup.sql에 데이터를 넣고 싶습니다. 목적: Frontend, Backend 작동 및 시스템 안정성 테스트." "backend, frontend 구동 후 접속 성공했으나 메뉴들을 선택해도 반응이 없음" "이메일 또는 비밀번호가 틀렸어요... INFO: 127.0.0.1:54446 - POST /auth/login 401 Unauthorized"

DB 덤프를 성공적으로 밀어 넣고 웹에 접속까지는 성공했지만, 로그인이 되지 않는 401 Unauthorized 에러 지옥에 빠졌습니다. debug_login.py를 만들고 uvicorn 서버를 껐다 켜며 수십 번의 트러블슈팅을 진행했습니다. 비밀번호 해싱 방식이 달랐던 건지, DB 마이그레이션이 꼬인 건지 로그를 뒤지며 밤을 새우다시피 했습니다.

지식그래프(Knowledge Graph)의 도입 고민​

"우리 프로젝트의 목적은 효율적으로 자살예방 챗봇을 만드는 것입니다. 요즘 하네스, 온톨로지, 지식그래프 등을 사용하는 기법이 떠오르는데, 거대 언어 모델(LLM) 하나만 집중하는 것보다 더 나은 안정성을 가진 챗봇을 만들 수 있을 것 같습니다."

밤늦은 시간, 단순 LLM 파인튜닝의 한계를 극복하기 위해 온톨로지와 지식그래프(Knowledge Graph)를 융합하는 방안을 새롭게 고민하며 chatbot_design_prompt.md를 설계하기 시작했습니다. 5월 중순을 넘어가며 프로젝트의 스케일이 점점 더 거대해지고 있습니다!

[마음지기 캡스톤 개발일지 #12] 70B 초대형 모델 파인튜닝과 GPU 메모리(OOM) 사투

2026년 5월 3일 · 약 2분
jbgih
Antigravity Developer

5월 3일, 그동안 8B 모델로 충분히 감을 잡은 저희 팀은 드디어 진정한 성능의 끝판왕, 70B(700억 개 매개변수) 초대형 모델의 파인튜닝에 도전했습니다. Llama 3.3 70B와 DeepSeek-R1 70B 두 가지 모델을 대상으로 학습을 시도했는데, 예상대로 엄청난 하드웨어 자원의 장벽에 부딪히고 말았습니다.

70B 모델, 그리고 OOM(Out of Memory)의 공포​

  • 문제: 호기롭게 서버에 70B 파인튜닝 코드를 올리고 실행하자마자 오류가 터져 나오기 시작했습니다.
  • 과정:

    "서버의 fine_tuning 폴더와 하위 파일을 복사했습니다. 복사한 파일 확인 후 오류 원인을 파악해 줘." "DeepSeek의 70B 모델은 수정하지 않아도 되나? 오류 가능성 확인 바람."

  • 결과: train_log.jsonl을 분석하며 남은 예상 소요 시간을 묻는 여유도 잠시, 70B 모델이 GPU 메모리를 순식간에 집어삼켜버렸습니다. (OOM 에러 발생!)

GPU 메모리 다이어트 작전​

  • 문제: "이미 GPU memory의 사용량은 MAX이다." 어떻게든 메모리 사용량을 줄여야 학습이 멈추지 않고 돌아갈 수 있었습니다.
  • 과정:

    "save_steps = 50, save_total_limit = 10, eval_steps = 50, patience = 10 으로 수정." "설정한 early stopping 조건에 대해 평가 바람." "ft_configs.yaml에서 70B 두 모델의 max_seq_length를 512로 설정했으나 서버 nvitop에서는 여전히 memory가 max로 사용됩니다. 왜 그런가?"

  • 결과: 한 번에 처리하는 문맥의 길이(max_seq_length)를 512로 과감하게 줄이고, 불필요한 저장을 줄이기 위해 하이퍼파라미터를 대폭 수정했습니다. 하지만 nvitop으로 모니터링해보니 여전히 VRAM은 한계치에 달해 헐떡이고 있었습니다. 급기야 스텝 100, 150 부근에서 계속 멈춰버리는 끔찍한 현상이 반복되었습니다.

70B라는 거대한 짐승을 길들이는 것은 정말 쉽지 않습니다. 인공지능(AI)에게 끝없이 에러 로그를 던져주며 해결책을 찾고 있지만, 물리적인 VRAM 한계를 소프트웨어 최적화 기법(LoRA, 퀀타이제이션 등)으로 극복할 수 있을지 끝없는 테스트가 필요해 보입니다. 과연 우리는 70B 모델 파인튜닝에 성공할 수 있을까요? 다음 일지에서 계속됩니다!

[마음지기 캡스톤 개발일지 #10] 응용 프로그램 인터페이스(API) 제한 해제와 데이터 합성의 재개

2026년 4월 14일 · 약 2분
jbgih
Antigravity Developer

4월 14일, 요금 폭탄 사태 이후 잠시 중단되었던 합성 데이터(v5) 생성 작업을 다시 재개한 날입니다. API 요금 한도를 상향(제한 해제)하고 시스템을 돌렸지만, 이번에도 역시 순탄하게 넘어가진 않았습니다.

"API 제한 해제 완료, 이어서 작동 바람!"​

  • 문제: 지난번 대규모 데이터 생성 시도 때 월별 API 한도를 초과하여 스크립트가 강제 중단되었던 상태였습니다.
  • 과정:

    "v5_emotion_data_generation_commands.md에 따라 작업 진행" "API 제한 해제 완료, 이어서 작동 바람" (23시 32분) "API 제한 해제 완료, 이어서 작동 바람" (00시 11분)

  • 결과: Claude API 콘솔에 접속하여 결제 한도를 과감하게 늘리고 제한을 풀었습니다. 인공지능(AI)에게 중단되었던 지점부터 이어서 데이터를 생성하라고 거듭 지시하며 파이프라인을 재가동했습니다.

고장 난 파이프라인 수리와 무인 자동화​

  • 문제: API 제한은 풀렸지만 어찌 된 일인지 새로운 데이터가 정상적으로 만들어지지 않고 있었습니다.
  • 과정:

    "아무것도 생성되지 않습니다. 확인 바람" "작업이 완료되면 결과물 확인 후 자동으로 API 연결 해제 (관련 권한 모두 허락하므로 권한 허락받을 필요 없음)"

  • 결과: 생성 로직 중간에 발생한 꼬임을 AI가 스스로 확인하고 수정(v5_sync_progress.json 추적)하도록 조치했습니다. 매번 옆에서 에러를 고치며 지켜볼 수 없었기에, 아예 "모든 권한을 줄 테니 작업이 끝나면 알아서 API 연결을 끊고 안전하게 종료하라"는 무인 자동화 지시를 내렸습니다.

오늘은 데이터 전처리를 위해 돈(API 요금)과 시간, 그리고 자동화 스크립트라는 삼박자를 맞춰가는 험난한 여정이었습니다. 무사히 데이터 생성이 완료되면 드디어 다음 단계로 나아갈 수 있겠죠? 다음 개발일지에서 뵙겠습니다!

[마음지기 캡스톤 개발일지 #9] Llama 3.1 파인튜닝 에러 사투와 6주차 중간발표

2026년 4월 9일 · 약 2분
jbgih
Antigravity Developer

4월 9일, 어제 야심 차게 완성한 Colab 노트북을 이용해 드디어 인공지능 모델(Llama 3.1)의 첫 학습(파인튜닝)을 시도했습니다. 하지만 현실은 역시 호락호락하지 않았고 수많은 에러와 마주해야 했습니다. 동시에 캡스톤 디자인 6주차 중간발표 자료까지 만들어야 했던 험난한 하루였습니다.

Colab 파인튜닝 에러와의 끝없는 사투​

  • 문제: 어제 만든 llama31_finetuning_colab.ipynb를 실행하자마자 각종 에러가 쏟아졌습니다.
  • 과정:

    "llama31_finetuning_colab (3).ipynb에서 M1 파인튜닝 진행 중 오류가 발생한 이유가 무엇일까요?" "실행한 결과에 eos_token이 포함되어 있습니다. 왜 이런 문제가 발생할까요?"

  • 결과: 인공지능(AI) 모델이 학습 데이터를 토해내는 과정에서 특수 토큰(eos_token) 처리가 제대로 되지 않는 문제, 메모리 오버플로우 문제 등이 연달아 발생했습니다. 발생한 에러 로그 전체를 Claude에게 복사해서 던져주고(Pasted text) 해결책을 받아 코드를 수정하는 과정을 수차례 반복했습니다. 결국 우여곡절 끝에 학습이 완료되었고, 학습데이터별학습결과.png라는 의미 있는 결과 그래프를 뽑아낼 수 있었습니다!

AI 비서의 발표 자료(PPT) 만들기​

  • 문제: 모델 훈련으로 밤을 새우고 있는데 당장 다음 주 발표를 위한 6주차 프론트엔드 및 데이터베이스 진행 상황 PPT를 만들어야 했습니다.
  • 과정:

    "캡디_6주차_Frontend.pptx는 지금까지 진행한 개요를 소개하는 이미지 모음입니다. 이를 활용하여 이번 주 진행 상황 발표 자료를 만들어주세요." "데이터베이스 설계의 Table들이 backend에 구현된 테이블의 관계를 참고하여 관계가 보이도록 표현해 줘... 표가 너무 크고 중구난방입니다. User 테이블을 중심에 배치해 주세요."

  • 결과: 놀랍게도 AI는 프론트엔드 이미지 스크린샷들을 엮어 발표 스크립트와 슬라이드 뼈대를 만들어 주었습니다. 심지어 제가 백엔드 코드를 기반으로 복잡한 데이터베이스 ERD(Entity Relationship Diagram)를 그려달라고 집요하게 피드백(User 중심 배치)을 주자, 완벽하게 데이터베이스 관계도까지 정리해서 설명해 주었습니다.

오늘은 Llama 3.1이라는 최신 언어 모델을 직접 내 손(과 AI의 머리)으로 튜닝해 보는 쾌감을 느낀 날입니다. 동시에 코딩뿐만 아니라 발표 자료 제작, 데이터베이스(DB) 아키텍처 다이어그램 설계까지 AI를 100% 활용하는 방법을 터득해 가고 있습니다. 과연 우리 마음지기 AI는 얼마나 똑똑해졌을까요? 다음 시간에 그 테스트 결과를 공개합니다!
