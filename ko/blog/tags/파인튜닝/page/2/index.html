[마음지기 캡스톤 개발일지 #13] 70B 학습의 한계와 중소형 모델(HCX, Qwen) 우회 전략

2026년 5월 4일 · 약 2분
jbgih
Antigravity Developer

70B라는 거대한 모델의 파인튜닝 과정에서 발생한 OOM(메모리 부족) 지옥을 경험한 5월 4일, 저희는 과감한 전략 변경을 시도했습니다. 70B 모델(Llama3.3, DeepSeek-R1)은 배치 사이즈를 극단적으로 줄여 겨우 checkpoint-1200, 1300까지 진행시켰지만, 학습 시간이 너무 오래 걸려 효율이 극악이었습니다.

중소형 모델(1.5B ~ 9B)로 눈을 돌리다​

물리적인 서버 자원과 캡스톤 프로젝트의 마감 기한을 고려했을 때, 70B에만 매달리는 것은 위험하다고 판단했습니다. 그래서 HCX-Omni-8B, Qwen35-9B, HCX-Text-1.5B 와 같은 상대적으로 가벼운 중소형 모델들로 파인튜닝 대상을 선회하여 실험을 시작했습니다.

"현재 지정한 하이퍼파라미터로 HCX-Omni-8B, Qwen35-9B, HCX-Text-1p5B를 학습시키는데 시간이 오래 걸리는데, 보편적으로 모델별로 이러한 파라미터가 사용되는가?" "이 batch size 상향이 학습에 어떠한 영향을 미치나요?"

작은 모델이라고 해서 모든 것이 순조로운 것은 아니었습니다. 빠른 학습을 위해 배치 사이즈(Batch Size)를 상향 조정해 보고, 모델 크기에 맞는 하이퍼파라미터 최적화 값을 찾아 AI와 끝없는 토론을 이어갔습니다. 가장 작은 모델인 HCX-Text-1.5B의 학습 결과를 먼저 뽑아내어 성능 평가를 진행하며 튜닝의 방향성을 잡아나갔습니다.

체크포인트 저장 오류와 커널 버전 문제​

HCX-Omni-8B 학습을 순조롭게 진행하던 중, 50 스텝에서 체크포인트를 저장하려다 또 다른 암초를 만났습니다.

[RANK 0] Detected kernel version 5.4.0, which is below the recommended minimum of 5.5.0; this can cause the process to hang.
...
![사진 02](./images/02_error.png)

JSONDecodeError Traceback (most recent call last)
---> 60 trainer.train(resume_from_checkpoint=...)

운영체제의 커널 버전이 낮아 프로세스가 멈출 수 있다는 경고와 함께, 저장된 체크포인트의 JSON 파일이 깨져서(JSONDecodeError) 학습을 재개하지 못하는 끔찍한 에러였습니다.

"현재 모델들이 학습 중 중단되면 중단된 부분에서 다시 학습을 시작하나요?"

다행히 허깅페이스 Trainer는 체크포인트부터 이어서 학습(resume_from_checkpoint)하는 기능을 제공하지만, 그 체크포인트 파일 자체가 손상되면 말짱 도루묵이 됩니다. 모델 크기를 줄였음에도 여전히 프레임워크와 인프라 단에서 발생하는 수많은 에러들과 씨름하며 하루를 꼬박 보냈습니다. 과연 안정적인 학습 궤도에 오를 수 있을까요?

[마음지기 캡스톤 개발일지 #12] 70B 초대형 모델 파인튜닝과 GPU 메모리(OOM) 사투

2026년 5월 3일 · 약 2분
jbgih
Antigravity Developer

5월 3일, 그동안 8B 모델로 충분히 감을 잡은 저희 팀은 드디어 진정한 성능의 끝판왕, 70B(700억 개 매개변수) 초대형 모델의 파인튜닝에 도전했습니다. Llama 3.3 70B와 DeepSeek-R1 70B 두 가지 모델을 대상으로 학습을 시도했는데, 예상대로 엄청난 하드웨어 자원의 장벽에 부딪히고 말았습니다.

70B 모델, 그리고 OOM(Out of Memory)의 공포​

  • 문제: 호기롭게 서버에 70B 파인튜닝 코드를 올리고 실행하자마자 오류가 터져 나오기 시작했습니다.
  • 과정:

    "서버의 fine_tuning 폴더와 하위 파일을 복사했습니다. 복사한 파일 확인 후 오류 원인을 파악해 줘." "DeepSeek의 70B 모델은 수정하지 않아도 되나? 오류 가능성 확인 바람."

  • 결과: train_log.jsonl을 분석하며 남은 예상 소요 시간을 묻는 여유도 잠시, 70B 모델이 GPU 메모리를 순식간에 집어삼켜버렸습니다. (OOM 에러 발생!)

GPU 메모리 다이어트 작전​

  • 문제: "이미 GPU memory의 사용량은 MAX이다." 어떻게든 메모리 사용량을 줄여야 학습이 멈추지 않고 돌아갈 수 있었습니다.
  • 과정:

    "save_steps = 50, save_total_limit = 10, eval_steps = 50, patience = 10 으로 수정." "설정한 early stopping 조건에 대해 평가 바람." "ft_configs.yaml에서 70B 두 모델의 max_seq_length를 512로 설정했으나 서버 nvitop에서는 여전히 memory가 max로 사용됩니다. 왜 그런가?"

  • 결과: 한 번에 처리하는 문맥의 길이(max_seq_length)를 512로 과감하게 줄이고, 불필요한 저장을 줄이기 위해 하이퍼파라미터를 대폭 수정했습니다. 하지만 nvitop으로 모니터링해보니 여전히 VRAM은 한계치에 달해 헐떡이고 있었습니다. 급기야 스텝 100, 150 부근에서 계속 멈춰버리는 끔찍한 현상이 반복되었습니다.

70B라는 거대한 짐승을 길들이는 것은 정말 쉽지 않습니다. AI에게 끝없이 에러 로그를 던져주며 해결책을 찾고 있지만, 물리적인 VRAM 한계를 소프트웨어 최적화 기법(LoRA, 퀀타이제이션 등)으로 극복할 수 있을지 끝없는 테스트가 필요해 보입니다. 과연 우리는 70B 모델 파인튜닝에 성공할 수 있을까요? 다음 일지에서 계속됩니다!

[마음지기 캡스톤 개발일지 #9] Llama 3.1 파인튜닝 에러 사투와 6주차 중간발표

4월 9일, 어제 야심 차게 완성한 Colab 노트북을 이용해 드디어 인공지능 모델(Llama 3.1)의 첫 학습(파인튜닝)을 시도했습니다. 하지만 현실은 역시 호락호락하지 않았고 수많은 에러와 마주해야 했습니다. 동시에 캡스톤 디자인 6주차 중간발표 자료까지 만들어야 했던 험난한 하루였습니다.

Colab 파인튜닝 에러와의 끝없는 사투​

  • 문제: 어제 만든 llama31_finetuning_colab.ipynb를 실행하자마자 각종 에러가 쏟아졌습니다.
  • 과정:

    "llama31_finetuning_colab (3).ipynb에서 M1 파인튜닝 진행 중 오류가 발생한 이유가 무엇일까요?" "실행한 결과에 eos_token이 포함되어 있습니다. 왜 이런 문제가 발생할까요?"

  • 결과: AI 모델이 학습 데이터를 토해내는 과정에서 특수 토큰(eos_token) 처리가 제대로 되지 않는 문제, 메모리 오버플로우 문제 등이 연달아 발생했습니다. 발생한 에러 로그 전체를 Claude에게 복사해서 던져주고(Pasted text) 해결책을 받아 코드를 수정하는 과정을 수차례 반복했습니다. 결국 우여곡절 끝에 학습이 완료되었고, 학습데이터별학습결과.png라는 의미 있는 결과 그래프를 뽑아낼 수 있었습니다!

AI 비서의 발표 자료(PPT) 만들기​

  • 문제: 모델 훈련으로 밤을 새우고 있는데 당장 다음 주 발표를 위한 6주차 프론트엔드 및 데이터베이스 진행 상황 PPT를 만들어야 했습니다.
  • 과정:

    "캡디_6주차_Frontend.pptx는 지금까지 진행한 개요를 소개하는 이미지 모음입니다. 이를 활용하여 이번 주 진행 상황 발표 자료를 만들어주세요." "데이터베이스 설계의 Table들이 backend에 구현된 테이블의 관계를 참고하여 관계가 보이도록 표현해 줘... 표가 너무 크고 중구난방입니다. User 테이블을 중심에 배치해 주세요."

  • 결과: 놀랍게도 AI는 프론트엔드 이미지 스크린샷들을 엮어 발표 스크립트와 슬라이드 뼈대를 만들어 주었습니다. 심지어 제가 백엔드 코드를 기반으로 복잡한 데이터베이스 ERD(Entity Relationship Diagram)를 그려달라고 집요하게 피드백(User 중심 배치)을 주자, 완벽하게 데이터베이스 관계도까지 정리해서 설명해 주었습니다.

오늘은 Llama 3.1이라는 최신 언어 모델을 직접 내 손(과 AI의 머리)으로 튜닝해 보는 쾌감을 느낀 날입니다. 동시에 코딩뿐만 아니라 발표 자료 제작, DB 아키텍처 다이어그램 설계까지 AI를 100% 활용하는 방법을 터득해 가고 있습니다. 과연 우리 마음지기 AI는 얼마나 똑똑해졌을까요? 다음 시간에 그 테스트 결과를 공개합니다!

[마음지기 캡스톤 개발일지 #8] API 요금 폭탄 사태와 Colab 파인튜닝 준비

2026년 4월 8일 · 약 2분
jbgih
Antigravity Developer

4월 8일은 마음지기 프로젝트를 진행하면서 가장 큰 위기이자 '웃픈' 해프닝이 발생한 날입니다. 바로 Claude API 월별 한도 초과 및 요금 폭탄 사태입니다.

백그라운드의 배신: "10건 생성에 1달러라니?"​

  • 문제: 어제 최적화를 마쳤다고 안심하고 대규모 테스트 데이터셋 생성 스크립트를 백그라운드에 켜둔 채 방치했습니다.
  • 과정:

    "문제: 월별 한도를 초과하여 비용이 청구되고 있음. 백그라운드로 API가 작동하는 줄 알고 냅뒀는데 이런 일이 벌어졌음." "아니 10건 생성하는데 1달러가 소비되는 게 말이 되나?"

  • 결과: LLM으로 고품질 상담 데이터를 합성(Synthesis)하는 과정에서 프롬프트의 컨텍스트(입력 토큰)가 누적되면서 비용이 기하급수적으로 늘어난 것입니다. 월별 결제 한도가 초과되어 스크립트가 멈추는 사태가 벌어졌고, 결국 AI에게 "실시간으로 예상 소비량과 비용, 진행 상황을 콘솔에 찍어주고, 한도 초과를 방지하는 기능을 당장 추가하라"라고 긴급 지시를 내렸습니다. 클라우드나 API를 사용할 때 요금 모니터링이 얼마나 중요한지 뼈저리게 느꼈습니다.

Llama 3.1 훈련을 위한 Colab 노트북 작성​

  • 문제: 데이터가 준비되어 가고 있으니, 이제 실제로 Llama 3.1 모델을 파인튜닝(Fine-Tuning)할 코드가 필요했습니다. 로컬 PC의 GPU로는 어림도 없기 때문에 Google Colab 환경을 사용해야 했습니다.
  • 과정:

    "llama31_finetuning_experiment_plan_revised.md을 Colab에서 진행하기 위한 python notebook을 작성해 주세요." "훈련 data를 train/val/test가 아닌 train/val로만 분할하고 9:1 비율로 나눈다."

  • 결과: AI가 스스로 훈련 계획서를 읽고 llama31_finetuning_colab.ipynb라는 완벽한 주피터 노트북 코드를 짜주었습니다. Unsloth 등 최신 경량화 라이브러리를 세팅하고, 데이터셋을 9:1 비율로 쪼개어 학습과 검증에 사용하는 로직까지 완벽하게 구현했습니다.

오늘은 API 요금 폭탄이라는 무시무시한 신고식을 치르며 프로젝트의 현실적인 장벽을 극복해 낸 하루였습니다. 하지만 그 대가로 훌륭한 데이터셋과 파인튜닝용 Colab 노트북까지 완성되었습니다. 드디어 다음 단계는 진짜 인공지능 모델을 훈련(Training)시키는 것입니다!

[마음지기 캡스톤 개발일지 #4] 파인튜닝 데이터 전처리 본격 가동

데이터 전처리 계획에 따른 자동화 실행​

  • 문제: 모델을 파인튜닝하기 위해서는 사용자의 발화와 챗봇의 응답이 담긴 원시 데이터를 Llama 3.1이 이해할 수 있는 특수한 JSONL 형식으로 완벽하게 변환해야 했습니다.
