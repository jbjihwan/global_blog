## 1. Selección del 4º modelo de fine-tuning e introducción de la arquitectura Safety Wrapper

### 1.1. Derivación de la proporción de datos óptima: Adopción del modelo mixto 2:1
Como resultado del 4º experimento de Fine-Tuning, un modelo de lenguaje grande (LLM) configurado con una proporción de 2:1 de conjuntos de datos de 'diálogo emocional' y 'diálogo cotidiano' registró los índices de rendimiento más altos en términos de comprensión de la intención del enunciado del usuario y capacidad de empatía. En consecuencia, este modelo fue adoptado finalmente como el modelo de inferencia principal para el servicio Maeumjigi.

### 1.2. Solución de problemas (Troubleshooting): Alucinación (Hallucination) y límites en la respuesta a enunciados de alto riesgo
Debido a la naturaleza del dominio del chatbot de prevención del suicidio y asesoramiento psicológico, las alucinaciones o las respuestas inapropiadas del modelo de inteligencia artificial (IA) pueden llevar a resultados fatales. Con la estructura exclusiva del LLM principal, era difícil garantizar siempre una respuesta segura y estandarizada a los enunciados que contenían intenciones suicidas (Active Suicidality) de usuarios en grupos de alto riesgo de depresión.

### 1.3. Solución (Solution): Construcción de la canalización Safety Wrapper
Para bloquear fundamentalmente estos riesgos, diseñamos y aplicamos una capa **Safety Wrapper (módulo de filtro de seguridad)** que envuelve las etapas de entrada/salida (I/O) del modelo principal.

- **Verificación de Input:** Analiza el texto de entrada del usuario para evaluar si se detectan palabras clave relacionadas con la autolesión o síntomas graves de depresión.
- **Control de Output y cambio de protocolo:** Si se determina que es una situación de alto riesgo, se omite (Bypass) el proceso normal de generación de texto del LLM, y la canalización se reconfigura para devolver inmediatamente una respuesta de seguridad codificada y orientación vinculada a expertos, basadas en el **protocolo de respuesta a crisis (Resource Inquiry Cues)** predefinido en el sistema.

En esta publicación, tratamos el progreso del cuarto fine-tuning (`fine_tuning_4`) del proyecto Maeumjigi y el proceso de experimentación de optimización de la mezcla del conjunto de datos para resolver el problema de sobreajuste (overfitting) del modelo de inteligencia artificial (IA).

## 1. Problema: Sesgo hacia el dominio de la conversación emocional y sobreajuste

Durante las pruebas del tercer modelo con fine-tuning (`fine_tuning_3`), descubrimos un fenómeno fatal de sobreajuste (overfitting) en el que la calidad de las respuestas del modelo estaba excesivamente sesgada hacia el dominio de la asesoría emocional. 

Como resultado de realizar el fine-tuning únicamente con el conjunto de datos `haiku_pred` existente, se produjo un problema en el que el modelo respondía con la personalidad de un asesor excesivamente serio y pesado, incluso cuando el usuario hacía preguntas cotidianas como "¿Cómo está el clima hoy?" o "¿Qué deberíamos comer?". Este es un fenómeno en el que el modelo base pierde su capacidad original para la conversación diaria de propósito general durante el proceso de aprendizaje del dominio objetivo (asesoría), y era un desafío que debía resolverse necesariamente para lograr la intención de planificación original de "un asesor de prevención del suicidio que transmite una cálida empatía".

## 2. Implementación: Construcción de un conjunto de datos emocionales propio (v6) de 10,000 casos

### Tubería de datos a gran escala utilizando Anthropic Batch API
Para resolver el problema anterior y mejorar la calidad del aprendizaje, procedimos a construir un conjunto de datos propio a gran escala (`Emotion_train_dataset_v6.jsonl`) utilizando el modo Batch de la API de Anthropic (Claude 3 Haiku). 

- **Especificaciones de los datos (Data Specification)**: Promedio de 500 tokens por dato (unificado a un máximo de 512 tokens), aplicación de un total de 20 tipos de personalidades detalladas.
- **Tamaño objetivo (Target Size)**: 10,000 casos.

### Solución de problemas (Troubleshooting): Imposibilidad de rastrear el procesamiento asíncrono y aparición de datos faltantes
Aunque introdujimos el modo Batch de la API para lograr eficiencia de costos, hubo un problema por el cual no podíamos rastrear el progreso y el consumo de créditos en tiempo real debido a la naturaleza del procesamiento asíncrono en segundo plano. Esto provocó la pérdida de algunos datos, pero desarrollamos un script de Python adicional (`fill_v6.py`) que analiza los resultados de la respuesta asíncrona para identificar los elementos faltantes y realizar llamadas a la API complementarias, logrando construir perfectamente el conjunto de datos de alta calidad objetivo de 10,000 casos.

## 3. Experimento principal: Optimización de la proporción de mezcla de datos (Data Mixing) para fine_tuning_4

Con base en el conjunto de datos emocionales v6 recién construido, comenzamos a diseñar el experimento para el cuarto fine-tuning (`fine_tuning_4`). 

El núcleo de este fine-tuning es alejarse del ajuste de hiperparámetros existente, como el valor Alpha de LoRA, y equilibrar el rendimiento específico del dominio y el rendimiento de propósito general en función de la **proporción de mezcla del conjunto de datos de entrenamiento (Data Mixing Ratio)**. Con el fin de mezclar y entrenar datos de conversación diaria como un tipo de regularización (Regularization), construimos conjuntos de datos de entrenamiento en las siguientes tres proporciones:

- `mixed_7_3` (Emocional 7 : Cotidiano 3)
- `mixed_5_5` (Emocional 5 : Cotidiano 5)
- `mixed_2_1` (Emocional 2 : Cotidiano 1)

Actualmente, utilizando los 3 tipos de conjuntos de datos anteriores, estamos aplicando de lleno el cuarto fine-tuning al modelo `Qwen3.5-9B`. A través de la verificación de los modelos entrenados en cada proporción, planeamos derivar la proporción áurea de la mezcla de datos que armonice de manera ideal la "cotidianidad" del chatbot y la "experiencia" del asesor.

## 2. Troubleshooting de la migración de la base de datos del backend en PostgreSQL

### 2.2. Análisis de causas y solución (Solution)

- **Aplicación de la solución**: Reiniciamos el servidor Uvicorn y depuramos el historial de conflictos de migración entre el middleware de autenticación y el esquema de la base de datos comparándolos y corrigiéndolos decenas de veces a través de los registros de depuración, logrando finalmente resolver el problema de autenticación `401 Unauthorized` y confirmando la emisión exitosa de la sesión.

Como resultado de la evaluación cualitativa de los resultados del primer fine-tuning del modelo de inteligencia artificial (IA), se produjo un fenómeno en el que la longitud del texto generado era anormalmente corta en comparación con el modelo base (Base Model) y el contexto se cortaba a la mitad.

### Causa
La causa fue un error de cálculo en la proporción (Scaling Factor) de los valores `rank(r)` y `alpha` configurados durante el entrenamiento LoRA (Low-Rank Adaptation). 
Durante el entrenamiento inicial, se configuró como `r=8` y `alpha=16`, pero en la ecuación de actualización de pesos de LoRA, el scaling factor se determina mediante $\frac{\alpha}{r}$. Como norma general, es común configurar `alpha` igual a `rank` o darle el doble del valor para ajustar el scaling factor alrededor de 1.0~2.0. Sin embargo, debido a una confusión en la proporción de aplicación de la fórmula, la actualización de los pesos se configuró para que se suprimiera extremadamente o se reflejara excesivamente. Como resultado, el espacio de representación de características intermedias (Feature) se distorsionó, causando el problema de que el modelo no pudiera generar texto con una longitud suficiente y terminara anticipadamente (Early Stopping).

- **Problem**: Los datos existentes estaban clasificados solo con emociones unidimensionales, lo que limitaba la capacidad de reflejar el estado psicológico complejo del cliente. El enfoque anterior basado en reglas (Rule-based) o los métodos simples de filtrado de palabras no podían captar las emociones ocultas en el contexto.
- **Solution**: Adoptamos un enfoque utilizando el LLM como Data Annotator. En lugar de expresiones regulares, pasamos el script de conversación completo como un prompt a través de la API de Claude para que realizara una inferencia basada en el contexto, aumentando drásticamente la calidad del etiquetado. Filtramos solo los datos claros y excluimos los datos ambiguos que no entraban en la clasificación de emociones para eliminar el ruido.

### 2. Problema de facturación por uso de la API del LLM y explosión de Tokens (Token)
- **Problem**: En el proceso de enviar 100,000 datos de conversación a la API, el uso de Tokens aumentó exponencialmente. Originalmente, esperábamos que el uso de la API estuviera cubierto por la suscripción Claude Pro ($20 al mes) o que podríamos evitar el cargo utilizando Claude Code en lugar de la API de Anthropic. Sin embargo, la API de Anthropic llamada desde el script de automatización de Python facturó de forma completamente independiente como pago por uso (pay-as-you-go) basado en tokens. Como resultado, ocurrió el problema de que solo la ejecución de la lógica de prueba para 100,000 casos facturó rápidamente $10.27 (aproximadamente 14,000 KRW).
- **Solution**:
  1. En lugar de investigar exhaustivamente los 1 millón de casos, cambiamos la estructura del flujo de trabajo para seleccionar y procesar solo los datos mínimos válidos esenciales para el fine-tuning (ajuste fino) mediante el muestreo de datos.
  2. Establecimos una estrategia para minimizar la longitud del Token de entrada (Input Token) optimizando la estructura del prompt, reduciendo así los costos de llamadas a la API de los datos a procesar en el futuro junto con la optimización del modelo.

## 📝 Conclusión

A través del trabajo de hoy, logramos asegurar un conjunto de datos refinado de alta calidad (`v4_report.md`), pero sentimos profundamente la barrera realista de 'recursos informáticos y costos de la API' que es inevitable en el proceso de preprocesamiento de datos de Aprendizaje Profundo. Planeamos continuar mejorando el fine-tuning (ajuste fino) de Llama 3.1 manteniendo un equilibrio eficiente entre la calidad del modelo y el costo de procesamiento de datos.

Los requisitos de la aplicación estaban definidos, pero existía el problema de que la estructura de comunicación entre el cliente Android y el servidor backend, y el orden de implementación del módulo del rastreador (crawler), no estaban claros. Esto se utilizará como un hito clave para mantener el contexto durante el proceso futuro de programación en pareja (pair programming) con la IA.

### 2. Construcción de Fixtures para la validación del rastreador basada en TDD
Antes de implementar el módulo del rastreador que realiza un seguimiento de los cambios en el estado de las reservas en tiempo real, era necesario construir un entorno de pruebas.

#### 🚨 Solución de problemas: Inestabilidad en las pruebas del rastreador
- **Problema**: Enviar solicitudes continuamente al sitio web objetivo que está en servicio activo para probar la lógica de análisis del DOM del rastreador genera una carga innecesaria en el servidor objetivo, y es una causa de pruebas inestables (Flaky Tests) donde los resultados varían según el estado de la red.
- **Solución**: Eliminamos las dependencias externas y construimos un entorno de Mockup (Fixture) que opera de manera determinista en un entorno offline.
  
A través del comando `continue` en Claude Code, le indicamos que generara automáticamente datos HTML simulados para las pruebas de frontend y backend. En consecuencia, se construyeron Fixtures HTML precisos que representan los siguientes dos estados:
- `sample_page.html`: Estructura DOM de un estado donde las reservas están llenas y no hay asientos disponibles.
- `sample_page_changed.html`: Estructura DOM de un estado donde se ha producido una cancelación y el botón de reserva está activado.

Utilizando estos Fixtures, sentamos las bases de pruebas unitarias que permiten verificar de forma rápida y estable si el código del rastreador en el lado del servidor detecta con precisión el cambio de estado (reserva no disponible -> reserva disponible) del HTML DOM Tree y desencadena eventos de notificación, sin necesidad de comunicación de red real.

## 1. Objetivos de implementación y características principales (Features)

El objetivo principal del proyecto inicial era el desarrollo de una aplicación para Android que monitorizara el estado de las reservas en tiempo real de un sitio web específico (Convención de Defensa Nacional) y detectara cambios de estado.

- **Target System**: Sistema de reservas del sitio web de la Convención de Defensa Nacional

- **Architecture Draft**: Planificación de un planificador de rastreo web (crawler scheduler) para verificar el estado periódicamente y la estructura de integración con el cliente móvil (Android).

## 2. Configuración del entorno de desarrollo y stack tecnológico (Tech Stack)

Para maximizar la productividad inicial del proyecto, integramos Claude Code, un asistente de codificación de IA basado en CLI, en nuestro flujo de trabajo de desarrollo.

- **AI Agent**: Claude Code
- **Integration Test**: Para verificar la capacidad de procesamiento de lenguaje natural (NLP) en coreano y la comprensión del contexto del agente, probamos la capacidad de respuesta del sistema con un prompt inicial como `"¿Entiendes coreano?"`. Luego, introdujimos un prompt específico: `"Quiero crear una aplicación que envíe una alarma cuando cambie a 'disponible para reserva'. ## 3. Problemas y soluciones (Troubleshooting)

### Problem: Pérdida de contexto e inconsistencia en la generación automática masiva de código
Durante el proceso de desarrollo utilizando el agente, se anticipó que si se generaban automáticamente cantidades masivas de código, el agente podría olvidar los objetivos principales del proyecto o desviarse de las convenciones de codificación, causando problemas de alucinación (Hallucination) y fragmentación del código.

### Solution: Establecimiento de una estructura de control del agente basada en documentación de reglas declarativas (Rule-based Documentation)
Para controlar el radio de acción del agente y mantener forzosamente el contexto del proyecto, definimos documentos de reglas globales a nivel de repositorio para que funcionaran como prompts del sistema (system prompts).

- `Claude.md`: El documento maestro que especifica la lógica de negocio general y los requisitos del sistema del proyecto.
- `CLAUDE_coding_rule.md`: Un documento de reglas a nivel de análisis estático que el agente de IA debe cumplir estrictamente al escribir código, como convenciones de nomenclatura (naming conventions), estructura de directorios y manejo de excepciones.

Como resultado, pudimos establecer con éxito restricciones (Constraints) para que el agente dependiera de las reglas de los documentos de referencia durante el desarrollo, como se vio en respuestas como *"No recibiré alarmas... Construiré la aplicación de Android de acuerdo con Claude.md"*.
